1 La idea general

El sistema es una aplicación web de tres pisos. Cada piso tiene un trabajo distinto y solo habla con el de al lado:

NAVEGADOR
Frontend: HTML + CSS + JavaScript
3 páginas (index, login, panel)
→
SERVIDOR NODE.JS
Backend: Express
API REST en el puerto 3000
→
MYSQL (XAMPP)
Base de datos
proyecto_3d_mind, puerto 3306
La regla de oro: el navegador NUNCA habla directo con MySQL. Las páginas solo piden datos al servidor (API); el servidor es el único que consulta la base de datos. Así las contraseñas y la estructura de la BD nunca quedan expuestas al cliente.

Las capas del backend

2 Cómo se conectan las piezas

Frontend ↔ Backend (la API)

Una API (Application Programming Interface) es un conjunto de "endpoints": URLs del servidor que aceptan peticiones y devuelven datos en formato JSON.

  • El frontend usa fetch() de JavaScript para llamar a esas URLs.
  • Cada endpoint tiene un método HTTP: GET (leer), POST (crear/enviar), PUT (actualizar), DELETE (borrar).
  • Las peticiones llevan datos en el body (JSON) y el servidor responde con un código de estado: 200 ok, 400 datos inválidos, 403 sin permiso, 404 no existe, 500 error del servidor.
  • El frontend siempre envía el header x-id-usuario con el id del usuario en sesión; el backend lo usa para saber QUIÉN pide y si tiene permiso.

Backend ↔ Base de datos

El backend usa la librería mysql2. La clase BaseDatos mantiene un pool de conexiones: en vez de abrir y cerrar conexión en cada consulta (lento), mantiene varias abiertas y las presta/reutiliza. Los modelos hacen: obtenerConexion() → consulta → release().

Ejemplo real: qué pasa cuando alguien hace login

Siguiendo una petición de punta a punta:

// 1. FRONTEND (login.html): el usuario escribe usuario y clave y envía el form
const resultado = await usuarioFrontend.iniciarSesion(username, password);
//    -> app.js -> fetch POST http://localhost:3000/api/usuarios/login
//       body: { username, password, ip }
//       header: Content-Type: application/json, x-id-usuario (si hay sesión)

// 2. RUTA (rutas/usuarioRutas.js): POST /login no tiene middleware
router.post('/login', usuarioControlador.iniciarSesion);

// 3. CONTROLADOR (UsuarioControlador.iniciarSesion):
//    - valida campos, busca el usuario con el modelo
//    - bcrypt.compare(password, usuario.password) compara la clave con el hash
//    - si falla: incrementa intentos, a los 5 bloquea
//    - si acierta: genera sessionToken, registra en historial_acceso,
//      responde JSON { sessionToken, usuario: {...}, id_sesion, ... }

// 4. MODELO (Usuario.buscarPorUsername):
//    SELECT u.*, r.nombre_rol FROM usuario u
//    LEFT JOIN rol r ON u.id_rol_FK = r.id_rol WHERE u.username = ?
//    -> devuelve la fila (o null)

// 5. El frontend recibe el JSON, guarda la sesión en sessionStorage
//    y redirige a panel.html

3 Arranque y archivos base

Cómo se ejecuta el proyecto

  1. Encender MySQL en XAMPP (puerto 3306).
  2. La primera vez: npm install en la raíz (instala las librerías de package.json en node_modules/).
  3. Copiar backend/.env.example como backend/.env y ajustar la contraseña de MySQL si tiene una.
  4. Ejecutar npm start (equivale a node backend/server.js).
  5. Abrir http://localhost:3000 → la primera vez pide crear el administrador (setup).

Las variables del .env

El archivo backend/.env guarda la configuración sensible (nunca se sube a Git):

DB_HOST=127.0.0.1      # servidor MySQL
DB_PORT=3306          # puerto de MySQL (XAMPP)
DB_USER=root          # usuario de MySQL
DB_PASSWORD=          # contraseña de MySQL
DB_NAME=proyecto_3d_mind  # nombre de la base de datos
PORT=3000             # puerto del servidor Node

basedatos.js lee estas variables con process.env y tiene valores por defecto si faltan. server.js lee PORT.

4.1 El arranque: backend/server.js

Es el punto de entrada de TODO el backend. Al ejecutar node backend/server.js pasa esto en orden:

  1. Carga el .env con dotenv (las contraseñas de MySQL).
  2. Crea la clase Servidor: su constructor crea la app de Express, lee el puerto (3000 por defecto) y llama a configurarMiddleware() y configurarRutas().
  3. configurarMiddleware():
    • cors(): permite peticiones del frontend.
    • express.json(): convierte el body de las peticiones a objetos JS.
    • Encabezados anti-caché (no-store): el navegador NO guarda respuestas, clave para que el botón "atrás" no muestre datos viejos.
    • express.static('../frontend'): sirve los HTML/CSS/JS/img directo.
  4. configurarRutas(): conecta cada prefijo del API con su archivo de rutas (/api/usuarios, /api/historial, /api/roles, /api/tipos-documento, /api/auth) y las páginas (/, /login.html, /panel.html).
  5. inicializarDatos() (antes de abrir el puerto):
    • Si la tabla rol está vacía → inserta Administrador (id=1) y Operario de tienda (id=2).
    • Si tipo_documento está vacía → inserta CC, TI, CE.
    • Verifica que exista la columna debe_cambiar_password; si no, la crea con ALTER TABLE (migración automática).
    • Nunca crea usuarios: el primer admin se crea por el flujo de setup.
  6. iniciar(): llama a inicializarDatos() y luego app.listen(3000). El servidor queda escuchando en http://localhost:3000.
Detalle de Node: al final hace module.exports = new Servidor() - exporta una instancia ya creada, no la clase. Los controladores hacen lo mismo.

4.2 La conexión: backend/configuracion/basedatos.js

La clase BaseDatos es lo más simple del proyecto:

  • Constructor: arma la configuración leyendo process.env.DB_* (con valores por defecto: host 127.0.0.1, puerto 3306, usuario root, base proyecto_3d_mind) y crea el pool con mysql.createPool(config).
  • obtenerConexion(): pide una conexión prestada del pool.
  • cerrarPool(): cierra todo (casi nunca se usa).

¿Qué es un pool? En vez de abrir y cerrar una conexión TCP a MySQL en cada consulta (muy lento), mysql2 mantiene un grupo de conexiones abiertas y las presta y reutiliza. Cada modelo sigue el patrón: pedir → consultar → release() (devolver).

Al final exporta new BaseDatos(): los modelos hacen const bd = require('../configuracion/basedatos') y comparten la misma instancia.

5 Los modelos (la capa que habla con MySQL)

Un modelo = una clase que representa una tabla de la base de datos. Cada método hace una operación SQL y devuelve filas (arrays de objetos). El patrón es siempre:

const conexion = await bd.obtenerConexion();
const [filas] = await conexion.query('SELECT ... WHERE x = ?', [valor]);
conexion.release();
return filas;

El ? es un parámetro seguro: mysql2 lo reemplaza internamente y evita la inyección SQL (que alguien manipule la consulta escribiendo código en un campo).

5.1 modelos/Usuario.js - la clase más grande

El constructor copia cada campo de datos a this (id_usuario, cedula, nombre, email, username, password, estado, int_fallidos, debe_cambiar_password, id_rol_FK, id_tipo_doc_FK). Los métodos:

crear()

INSERT de usuario nuevo. Antes cifra la contraseña con bcrypt.hash(password, 10) (el 10 es el "costo": más alto = más seguro y más lento). Devuelve el id creado.

buscarPorUsername(username)

SELECT de UN usuario por username, con JOIN a rol para traer nombre_rol en la misma consulta. Devuelve la fila o null. Es la que usa el login.

verificarDuplicados(cedula, email, username)

SELECT que busca filas que coincidan con CUALQUIERA de los tres valores. La usa el registro para rechazar duplicados.

verificarDuplicadosExcluyendo(id, ...)

Igual pero con AND id_usuario != ? - para que al editar un usuario no se confunda consigo mismo.

obtenerTodos()

SELECT de todos los usuarios que NO estén "Eliminado", con JOINs a rol y tipo_documento para traer nombres legibles. Si el JOIN falla, reintenta con un SELECT simple (plan B defensivo).

obtenerPorId(id)

SELECT de un usuario por id. Devuelve la fila o null.

actualizar(id, datos)

UPDATE dinámico: siempre actualiza nombre/cedula/email/username/rol/tipo_doc; solo agrega password si viene con valor (y la cifra con bcrypt aquí mismo). Devuelve true si cambió algo.

incrementarIntentosFallidos(id) / reiniciarIntentos(id)

UPDATE de int_fallidos: +1 en un caso, =0 en el otro.

bloquear(id) / desbloquear(id)

UPDATE del estado. Bloquear solo si estaba 'Activo'; desbloquear solo si estaba 'Bloqueado' (y resetea int_fallidos a 0). Devuelven cuántas filas cambiaron - si da 0, el estado no permitía la operación.

eliminar(id)

UPDATE estado='Eliminado'. Es eliminación lógica: el registro sigue en la BD pero se oculta de las consultas. Nunca se borra físicamente.

cambiarPassword(id, passwordEncriptada)

UPDATE de la contraseña YA cifrada + pone debe_cambiar_password = 0.

contarNoEliminados()

SELECT COUNT de usuarios no eliminados. Devuelve 0 solo cuando el sistema está "virgen". La usa el setup inicial y setup-status.

5.2 modelos/HistorialAcceso.js

Registra cada inicio/cierre de sesión (auditoría):

  • crear(idUsuario, ip): INSERT con fecha actual, IP y usuario. Devuelve el id del registro (se usa para marcar la salida).
  • actualizarSalida(idSesion): UPDATE pone fecha_salida = ahora.
  • obtenerTodos(): SELECT de todo el historial con JOIN a usuario (nombre/username), del más reciente al más viejo.

5.3 modelos/Rol.js y modelos/TipoDocumento.js

Catálogos simples con tres métodos cada uno:

  • obtenerTodos(): SELECT de toda la tabla (alimenta los selects del formulario).
  • hayRoles() / hayTipos(): SELECT COUNT para saber si la tabla tiene datos.
  • insertarBasicos(): inserta los valores por defecto (2 roles / CC, TI, CE). Solo los usa server.js al arrancar.

6 Los controladores (la lógica de negocio)

El controlador recibe req (la petición: body, params, headers) y res (la respuesta). Su trabajo: validar entradas, llamar al modelo y devolver JSON con código HTTP (200 ok, 400 datos malos, 403 sin permiso, 404 no existe, 500 error).

6.1 controladores/UsuarioControlador.js - el más importante

Arriba del archivo hay una lista en memoria: 
const sesionesActivas = new Map();
Guarda token -> {id_usuario, fecha} de cada sesión iniciada. El token es aleatorio de 64 caracteres (crypto.randomBytes(32)). Se pierde al reiniciar el servidor (las sesiones no sobreviven reinicios).

El constructor hace bind de dos métodos porque Express los llama sin contexto y this se perdería: iniciarSesion y setupAdmin.

registrar(req, res) - POST /api/usuarios/registrar (solo admin)
  1. Valida cada campo: nombre ≥3 caracteres, cédula solo números, email con formato válido, username presente, contraseña ≥6, tipo doc y rol seleccionados.
  2. Llama verificarDuplicados y revisa fila por fila: cédula duplicada (no eliminada), email y username → rechaza con 400.
  3. Crea el Usuario. Detalle clave: si el rol es 2 (Operario), marca debe_cambiar_password = 1 - el operario DEBE cambiar su clave en el primer ingreso. El admin (rol 1) no.
  4. crear() lo guarda cifrado y responde "Usuario registrado con exito".
obtenerTodos(req, res) - GET /api/usuarios/obtener (solo admin)

Trae todos los usuarios, hace delete u.password en cada uno (nunca se envía la contraseña ni siquiera cifrada al frontend) y responde el array.

obtenerPerfil(req, res) - GET /api/usuarios/perfil

Lee el header x-id-usuario, busca ese usuario y devuelve sus datos sin password. Es lo que usa el operario para ver/editar su propia ficha sin ver a los demás.

actualizar(req, res) - PUT /api/usuarios/actualizar/:id

La lógica más delicada del sistema:

  1. Valida campos igual que registrar (la contraseña es opcional aquí).
  2. verificarDuplicadosExcluyendo(id,...) - mismo chequeo ignorando al propio usuario.
  3. Regla de autoedición: compara el id del endpoint con el header x-id-usuario. Si son el mismo usuario Y su rol NO es admin, ignora todos los campos que mandó el frontend y solo conserva la contraseña (un operario solo puede cambiar su clave). Además le prohíbe poner la misma contraseña que ya tiene.
  4. Si es admin editando a otro, sí se actualiza todo.
bloquear / desbloquear / eliminar

Wrappers simples sobre el modelo. Bloquear/desbloquear devuelven 400 si el estado actual no permite la operación. Eliminar revisa que no sea auto-eliminación (id del path == id_usuario_sesion del body).

cambiarPassword(req, res) - PUT /api/auth/cambiar-password

Lo usan el cambio obligatorio de primer ingreso Y el "modificar contraseña" del panel:

  1. Valida id, contraseña nueva ≥6 y que coincida la confirmación.
  2. Quién puede: el propio usuario con sesión, un admin (rol 1), o el flujo de primer ingreso (debe_cambiar_password = 1, sin sesión aún).
  3. Rechaza si la nueva es igual a la actual (bcrypt.compare).
  4. Cifra con bcrypt y llama modelo.cambiarPassword (apaga la bandera).
verificarAdminPassword(req, res) - POST /api/auth/verificar-admin

Recibe {id_usuario, password} y responde {autorizado: true} si la clave coincide. Es la "doble verificación" del frontend.

Devuelve 403 y no 401 a propósito: app.js trata cualquier 401 como "sesión inválida" y cerraría la sesión - una clave mal tipeada en la verificación tumbaría todo el panel.

Acepta cualquier usuario activo, no solo admin (sirve también para la reautenticación por inactividad del operario).

logout(req, res) - POST /api/auth/logout

Recibe el sessionToken y lo borra del Map sesionesActivas. También se usa con navigator.sendBeacon al cerrar la pestaña.

iniciarSesion(req, res) - POST /api/usuarios/login

El corazón del login:

  1. Valida que vengan username y password.
  2. buscarPorUsername → si no existe, 404.
  3. Si está 'Eliminado' → 403. Si está 'Bloqueado' → 403 con mensaje según int_fallidos.
  4. bcrypt.compare(password, usuario.password) compara el texto plano con el hash guardado.
  5. Si falla: incrementa intentos; si llega a 5 → bloquea + "Usuario bloqueado por superar 5 intentos". Si no → 401 "Le quedan N intentos".
  6. Si acierta: reinicia intentos a 0, calcula si debe cambiar contraseña, y llama responderSesionExitosa.
responderSesionExitosa(req, res, usuario, requiereCambio)

La usan tanto el login como el setup-admin:

  1. Normaliza la IP (::1 y ::ffff: → 127.0.0.1).
  2. Registra el ingreso en historial - si falla NO rompe el login (try/catch solo loguea). Guarda el id_sesion del historial para que el frontend marque la salida después.
  3. Genera sessionToken aleatorio y lo guarda en sesionesActivas.
  4. Responde JSON con sessionToken, ip, fecha_ingreso, id_sesion y el objeto usuario (id, nombre, username, id_rol, nombre_rol) - sin password.
setupStatus / setupAdmin

setupStatus (GET /api/auth/setup-status): devuelve {needsSetup: true} si no hay usuarios. Es lo primero que consulta index.html.

setupAdmin (POST /api/auth/setup-admin): crea el PRIMER admin. Si ya hay usuarios → 403 "El sistema ya fue configurado" (nadie puede reusarlo). Crea con rol=1, sin cambio de clave obligatorio, y llama responderSesionExitosa: el setup deja al admin LOGUEADO automáticamente.

6.2 controladores/HistorialControlador.js

  • registrarSalida(req, res) - POST /api/historial/salida: recibe id_sesion (el id del registro de historial, NO el token de sesión) y marca la fecha de salida.
  • obtenerTodos(req, res) - GET /api/historial/obtener: devuelve todo el historial. limitación Esta ruta NO tiene middleware de admin - cualquier sesión activa puede leerla.

6.3 controladores/RolControlador.js y TipoDocumentoControlador.js

Un solo método cada uno (obtenerTodos): llaman al modelo y devuelven el array. Solo sirven para llenar los <select> del formulario de usuarios.

7 Los middlewares (filtros de seguridad)

Un middleware es una función que corre antes del controlador. Si no llama next(), la petición se detiene ahí con un error.

middleware/verificarAdmin.js

Protege rutas de "solo administrador":

  1. Saca el id del usuario de donde sea: header x-id-usuario, query ?id_usuario o body.
  2. Si no hay id → 403 "se requiere una sesion activa".
  3. Busca el usuario en la BD. Si no existe o id_rol_FK !== 1 → 403.
  4. Si todo bien → next() y sigue al controlador.

middleware/verificarAdminOSelf.js

Más permisivo: deja pasar si es admin O si el usuario es él mismo (req.params.id del endpoint == su propio id). Es para PUT /actualizar/:id: el admin puede editar a cualquiera, el operario solo su ficha.

Punto débil a conocer: la "sesión" real es el header x-id-usuario con el id en texto plano. El servidor confía en ese número - no hay token firmado tipo JWT. El sessionToken existe en memoria pero los middlewares no lo verifican. Es una decisión de diseño simple del proyecto formativo (limitación reconocida).

9 El frontend: frontend/js/app.js

Es el "puente" entre las páginas y el API. Define clases que envuelven cada familia de endpoints. Al final se crean instancias globales que cualquier página puede usar tras cargar el script.

9.1 class Aplicacion - el que habla HTTP

peticion(endpoint, metodo, datos) - EL método clave
  1. Arma las opciones del fetch: método, header Content-Type: application/json y x-id-usuario con el id del usuario en sesión (lo saca de sesion.obtener()).
  2. Si hay datos, los convierte a JSON en el body.
  3. Hace el fetch a baseUrl + endpoint (baseUrl = http://localhost:3000/api).
  4. Manejo de 401: si el servidor responde 401 y había sesión, cierra sesión, guarda el aviso "La sesión se ha cerrado..." y redirige al login.
  5. Parsea el JSON; si la respuesta no fue ok, lanza un Error con error.mensaje (los controladores siempre devuelven {mensaje: "..."}).

obtenerIP(): consulta api.ipify.org para saber la IP pública del cliente (se envía al login para el historial). Si falla (sin internet), devuelve 127.0.0.1.

9.2 Las clases "Frontend" (una por recurso)

UsuarioFrontend, RolFrontend, TipoDocumentoFrontend, HistorialFrontend: son envoltorios finos - cada método llama a app.peticion(...) con el endpoint correcto. Ejemplos: iniciarSesion (primero obtiene la IP, luego POST /usuarios/login), obtenerTodos, actualizar(id, datos), eliminar(id, idSesion), registrarSalida(idSesion).

9.3 class Sesion - dónde vive la sesión

  • Clave usuario_sesion en sessionStorage (no localStorage): la sesión muere al cerrar la pestaña. En el constructor borra cualquier rastro viejo en localStorage.
  • guardar(datos): guarda el JSON de la sesión (usuario + token + ip + fecha).
  • obtener(): la lee y parsea; devuelve null si no hay.
  • cerrar(): la borra. estaActiva(): el guardián de todas las páginas.

Lo que se guarda (lo arma guardarSesion en login.html): {id_usuario, nombre, username, id_rol, nombre_rol, sessionToken, ip, fecha_ingreso}.

10 Las 3 páginas HTML

10.1 index.html - portada y setup inicial

Al cargar ejecuta iniciar(): consulta GET /api/auth/setup-status.

  • Si needsSetup === true (no hay usuarios): muestra "Antes debes registrarte como administrador" + formulario con nombre, cédula, email, username, contraseña x2 → setupAdmin() → el admin queda logueado automáticamente → panel.html.
  • Si ya hay usuarios: botón que va a login.html.
  • Si el servidor no responde: mensaje de error.

10.2 login.html - iniciar sesión

Al cargar: muestra aviso si viene aviso_sesion; si ya hay sesión → directo al panel; consulta setup-status y si needsSetup redirige a index.html.

Al enviar el formulario, tres resultados posibles:

  • requiereCambioPassword === true: abre el modal "Actualización obligatoria" (nueva contraseña + confirmar) → cambiarPassword → entra al panel.
  • Login normal: continuarAlPanel() → guarda sesión + id_sesion del historial → SweetAlert "Bienvenido" de 3s → panel.html.
  • Error: spinner fuera, animación shake del card, mensaje del backend ("usuario no existe", "le quedan N intentos", etc.).

El enlace "Olvidé mi contraseña" solo muestra un aviso: contacte al administrador.

Es una SPA (una sola página con "vistas" que se muestran/ocultan). Lo primero al cargar: si !sesion.estaActiva() → login. Nadie entra sin sesión.

La doble verificación (la seguridad más visible)

  • solicitarVerificacionAdmin(texto, accion, forzar): si la verificación sigue vigente (ventana de 10 minutos) ejecuta la acción directo; si no, abre el modal pidiendo la contraseña.
  • El modal no tiene botón de validar: validarVerificacion() se dispara sola 500ms después de dejar de escribir (debounce) o con Enter → POST /auth/verificar-admin. Si va bien: check verde ~300ms, cierra modal, marca 10 min más y ejecuta la acción pendiente.
  • Cuándo se exige SIEMPRE (ignora los 10 min): bloquear, desbloquear, operario cambiando su contraseña.
  • Cuándo usa la ventana de 10 min: entrar a Usuarios, nuevo, editar, eliminar.

Cierre de sesión e inactividad

  • Manual: botón → cerrarSesion() → logout backend + salida en historial + limpiar sessionStorage + avisar a otras pestañas + login.

Preguntas frecuentes sobre el sistema

Las dudas más comunes de alguien que está conociendo el proyecto, agrupadas por tema.

Sobre entrar y usar el sistema

¿Qué pasa la primera vez que abro el sistema?

index.html consulta GET /api/auth/setup-status. Si no hay usuarios en la BD, responde needsSetup: true y la página muestra el formulario para crear el primer administrador (nombre, cédula, email, username, contraseña). Al enviarlo, setupAdmin crea el usuario con rol Administrador y lo deja logueado automáticamente. A partir de ahí, el sistema ya pide login normal.

¿Por qué el operario debe cambiar la contraseña y el administrador no?

Es una regla de seguridad del negocio: cuando el admin crea un operario (rol 2), el backend marca debe_cambiar_password = 1. En su primer login, la respuesta trae requiereCambioPassword: true y login.html abre el modal "Actualización obligatoria" antes de dejarlo entrar. El admin (rol 1) se crea con la bandera en 0 porque se supone que él mismo eligió su clave en el setup.

¿Qué significan los estados Activo, Bloqueado y Eliminado?

Son los 3 valores del campo estado en la tabla usuario:

  • Activo: puede iniciar sesión normalmente.
  • Bloqueado: no puede entrar. Llega ahí por bloqueo manual del admin o automático tras 5 intentos fallidos. Solo el admin puede desbloquearlo.
  • Eliminado: eliminación lógica - el registro sigue en la BD pero desaparece de las consultas y el login lo rechaza. No se puede "deseliminar" desde el sistema.
¿Qué pasa si un usuario se equivoca la contraseña 5 veces?

Cada fallo llama incrementarIntentosFallidos. La respuesta le dice "Le quedan N intentos". Al llegar a 5, el backend ejecuta bloquear(): el estado pasa a 'Bloqueado' y a partir de ahí el login responde 403 "Usuario bloqueado por intentos fallidos" sin siquiera revisar la contraseña. Solo el admin puede desbloquearlo, y al hacerlo el contador vuelve a 0.

¿Qué pasa si cierro la pestaña o el navegador sin cerrar sesión?

Dos cosas pasan solas: (1) sessionStorage se destruye con la pestaña, así que al volver a abrirla no hay sesión y toca hacer login de nuevo; (2) el evento pagehide dispara un sendBeacon que llama /api/auth/logout y borra el token del Map sesionesActivas en el servidor. Si el navegador muere de golpe sin ejecutar pagehide, el token queda huérfano en memoria hasta que el servidor se reinicie (no pasa nada grave: la sesión del navegador ya no existe).

¿Por qué el botón "atrás" del navegador me regresa al login?

Por la protección anti-BFCache. El servidor envía headers no-store en todas las respuestas para que el navegador no guarde las páginas, y además panel.html escucha el evento pageshow: si la página fue restaurada desde la caché del navegador (e.persisted) o la sesión ya no existe, redirige al login con location.replace (sin dejar la página protegida en el historial).

¿Qué es la doble verificación de contraseña?

Antes de acciones sensibles (entrar a Usuarios, crear/editar/eliminar usuarios, bloquear/desbloquear, cambiar la propia clave), el sistema abre un modal pidiendo la contraseña del usuario en sesión y la valida contra el backend (POST /api/auth/verificar-admin). Si es correcta, la verificación queda vigente 10 minutos y no vuelve a pedirla para acciones normales. Bloquear/desbloquear y el cambio de clave del operario la piden siempre, sin importar los 10 minutos.

¿Qué pasa después de 5 minutos sin usar el sistema?

El panel programa dos temporizadores: a los 4.5 minutos aparece un aviso en pantalla, y a los 5 minutos se abre el modal de verificación con el modo esReautenticacion: "Tu sesión se bloqueó por inactividad, ingresa tu contraseña para continuar donde estabas". No se puede cerrar (sin X ni clic fuera) porque es obligatorio. Cualquier actividad del mouse/teclado reinicia los temporizadores. Si verificas bien, sigues trabajando; no perdiste la sesión.

¿Olvidé mi contraseña, qué hago?

El enlace "Olvidé mi contraseña" del login solo muestra un aviso: contacte al administrador. No hay recuperación por correo ni pregunta secreta - el admin debe entrar al módulo Usuarios y editar al usuario poniéndole una contraseña nueva (el campo de contraseña en edición es opcional; si lo dejas vacío conserva la actual).

¿Qué es "Módulo en actualización"?

El menú lateral tiene entradas para Pedidos, Ventas y Clientes que aún no están implementadas (el sistema real solo tiene Usuarios funcionando). Al hacer clic en ellas aparece un SweetAlert "Módulo en actualización" y el panel sigue en la vista de bienvenida. Las tablas de la BD para esos módulos ya existen pero están vacías.

Sobre usuarios y permisos

¿Quién puede crear, editar, bloquear o eliminar usuarios?

Solo el Administrador (rol 1). El backend lo refuerza con los middlewares verificarAdmin (registrar, listar, bloquear, desbloquear, eliminar) y verificarAdminOSelf (actualizar: admin o el propio usuario). El frontend también lo oculta: al operario ni siquiera le aparece el menú de Usuarios.

¿Qué puede editar un operario en su perfil?

Solo su contraseña. En "Mi Configuración" ve sus datos enmascarados de solo lectura y debe pasar la doble verificación para revelar los campos de contraseña. Aunque intente enviar otros campos, el controlador actualizar detecta que es autoedición de no-admin e ignora todo menos la contraseña.

¿Cómo sé qué rol tiene cada usuario?

El directorio de usuarios muestra la columna "Rol" con el nombre (nombre_rol viene del JOIN con la tabla rol). En la barra superior del panel también se ve el rol de la sesión. Internamente: id_rol_FK = 1 es Administrador, = 2 es Operario de tienda.

¿El administrador puede ver las contraseñas de los usuarios?

No, y no podría aunque quisiera. Las contraseñas se guardan con bcrypt: una "huella" irreversible. Ni el admin, ni la BD en texto plano, ni nadie puede recuperar la clave original - solo compararla con bcrypt.compare al hacer login o al verificar la doble verificación. Por eso la única forma de "recuperar" acceso es que el admin asigne una clave nueva.

¿Qué muestra la pestaña Historial de accesos?

La tabla historial_acceso: cada fila es un inicio de sesión con el nombre del usuario, fecha y hora de ingreso, fecha y hora de salida (si cerró sesión bien), y la IP desde donde se conectó. Se registra automáticamente en cada login (responderSesionExitosa) y la salida se marca al cerrar sesión (manual, por inactividad no - porque no cierra, o al cerrar pestaña si el sendBeacon alcanzó). Sirve como auditoría: quién entró, cuándo y desde dónde.

¿Puedo tener el sistema abierto en dos pestañas o dos computadores?

Sí. Cada pestaña/navegador tiene su propia sesión en su propio sessionStorage y su propio token en el Map del servidor (el Map acepta varios tokens a la vez). Si cierras sesión en una pestaña, las demás se enteran por el evento storage y también vuelven al login. Dos usuarios distintos pueden trabajar en paralelo sin problema - las consultas a MySQL son independientes.

Sobre el funcionamiento técnico

¿Qué valida el frontend y qué valida el backend?

El frontend valida para dar feedback inmediato: bordes rojos/verdes y mensajes mientras escribes (cédula numérica, email con formato, campos no duplicados contra la lista cargada, contraseña ≥6 y confirmación igual). Pero la seguridad REAL está toda en el backend: cada endpoint vuelve a validar campos, permisos de rol y duplicados en la BD. Aunque alguien llame la API a mano con otras herramientas (Postman, curl), el backend lo rechaza igual.

¿Qué pasa si el servidor se reinicia con usuarios conectados?

El Map sesionesActivas se vacía (los tokens se pierden), pero las sesiones en el sessionStorage de cada navegador siguen existiendo. El usuario podría seguir navegando porque el panel confía en sessionStorage, y la doble verificación seguiría funcionando porque va contra la BD. Lo que se pierde es el logout "limpio" del token (queda huérfano hasta reiniciar, que es lo mismo). Además, inicializarDatos() vuelve a correr al arrancar: vuelve a verificar roles, tipos de documento y la columna debe_cambiar_password (todo idempotente, no duplica nada).

¿El sistema necesita internet para funcionar?

Casi todo funciona sin internet porque todo está en localhost. Hay dos detalles: (1) las librerías SweetAlert2, Lucide, Animate.css y highlight se cargan desde CDN - sin internet las notificaciones y iconos no se verían (aunque el sistema seguiría respondiendo); (2) obtenerIP() consulta api.ipify.org para registrar la IP pública en el historial - si falla, usa 127.0.0.1 como fallback y el login funciona igual.

¿Puedo usar el sistema desde otro computador de la red?

El servidor Express escucha en localhost:3000 por defecto, así que solo es accesible desde la misma PC. Para acceso desde otro equipo habría que cambiar el bind del servidor y la baseUrl del frontend (que hoy está quemada como http://localhost:3000/api).

¿Qué hace reset_db.js y cuándo se usa?

Es un script manual de laboratorio (node backend/reset_db.js) que vacía las tablas de datos - usuarios, historial de accesos y las de módulos futuros - y reinicia el contador AUTO_INCREMENT. NO toca los catálogos (roles, tipos de documento). Se usa cuando quieren empezar el sistema de cero para una nueva configuración inicial o para limpiar datos de prueba.

¿Qué significan los colores rojo y verde en los campos del formulario?

Es la validación en tiempo real: verde + ✓ = el campo está bien (formato correcto y no duplicado), rojo + mensaje = hay un problema (cédula con letras, email mal formado, username ya existe, contraseñas que no coinciden, etc.). El debounce de 300ms evita validar en cada tecla - espera a que dejes de escribir. El formulario no deja guardar mientras haya campos en rojo.

¿Qué pasa si dos personas editan al mismo tiempo?

No hay control de concurrencia (bloqueos ni versionado): el último en guardar gana, sobrescribe lo que el otro escribió. Es una limitación típica de proyectos formativos con una sola tabla de usuarios y pocos usuarios simultáneos. En la práctica el volumen es bajo y el riesgo es mínimo.

¿Por qué el login dice "el usuario no existe" en vez de "contraseña incorrecta"?

Decisión de diseño (aunque revela si un username existe - una debilidad menor de seguridad llamada enumeración de usuarios). Ayuda al usuario a darse cuenta de un error de tipeo en el nombre. Si el usuario existe pero la clave está mal, el mensaje es distinto: "Usuario o contraseña incorrectos. Le quedan N intentos".

Sobre seguridad

¿Por qué el token de sesión no se usa para autorizar?

El sessionToken sirve para logout y control en memoria, pero los middlewares autorizan por el header x-id-usuario + consulta a la BD. Es simple pero tiene el punto débil de que el id viaja en texto plano (limitación reconocida del proyecto). Un diseño más robusto usaría JWT firmados o tokens de sesión verificados en cada petición.

¿Cómo evitan que roben la sesión?

Varias capas: sessionStorage muere al cerrar la pestaña; headers no-store + pageshow evitan que el botón atrás restaure la página; la doble verificación pide la clave para acciones sensibles; la inactividad de 5 min obliga a reautenticar; las contraseñas nunca viajan en texto plano (bcrypt). Limitación honesta: el x-id-usuario viaja en texto plano sin firma, así que alguien que lo manipule podría suplantar al usuario ante el API.

¿Por qué verificar-admin devuelve 403 y no 401?

Porque app.js trata cualquier 401 como "sesión inválida" y cierra sesión. Si la clave de verificación estuviera mal y devolviera 401, te sacaría del panel por un simple error de tipeo. Con 403 solo muestra "Contraseña incorrecta" y puedes reintentar sin perder la sesión.

¿Por qué no hay borrado físico de usuarios?

Eliminación lógica: conserva el historial de accesos (que tiene FK al usuario) y la auditoría. Un usuario "eliminado" ya no puede loguear (el login lo rechaza con 403) ni aparece en el directorio, pero su historial queda intacto para consultas. Además reset_db.js es la herramienta para vaciar datos de verdad cuando haga falta.

¿Qué pasa si alguien intenta entrar a panel.html sin login?
